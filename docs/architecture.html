Architecture

From a chat message to a motor command.

Five hops, one of which is the only place a safety decision can be enforced.

Data path

The five hops

  1. Telegram

    The operator sends plain text to a bot. Telegram is the whole user interface — there is no dashboard, no teleop, no joystick. Everything the operator can express, they express in a sentence.

  2. OpenClaw gateway

    The gateway receives the message, loads the session, and assembles the prompt. It reads every SKILL.md in the workspace so the model knows what exists. Critically, it also applies the tool profile: the list of tools this agent is permitted to call. This is the enforcement point.

  3. Dispatcher

    The language model reads the instruction, the skill descriptions, and whatever results came back from previous steps, then emits one tool call. It does not plan the whole task up front. It takes a step, reads the result, and decides again — which is what makes the loop closed rather than open.

  4. Skill execution

    A skill is a Python script in a virtual environment with the Unitree SDK installed. It runs to completion, prints a structured result line, and exits. All the domain logic — watchdog timing, yaw calibration, detection thresholds — lives here, where it can be tested, not in the model's head.

  5. DDS to the robot

    The script speaks to the Go2's high-level sport controller over DDS on a wired USB-Ethernet link. No ROS bridge is involved. Motion commands are resent continuously for the duration of the movement, because the controller's watchdog stops the robot roughly a second after the last command.

The enforcement point

Tool profiles

A tool profile is a list of tool identifiers the agent may call. Denials are evaluated after allowances, so a denied tool stays denied no matter how it was granted. Two details cost us time and are worth stating plainly.

Deny beats allow

If a tool appears in both lists, it is denied. This is what makes the profile a reliable floor rather than a suggestion — a broad group allowance cannot accidentally reintroduce something you removed.

Tool IDs are literal

Denying write does not deny apply_patch. They are separate identifiers and both can modify files. Every mutating tool has to be named, or denied as a group.

The working profile for Approach 1 is in the repository under config/. It is not reproduced here in full.

Network

Two interfaces at once

The workstation needs the robot and the internet simultaneously, on separate interfaces. The robot link must never become the default route, or API calls will be sent to a robot that has no idea what to do with them.

Not in the loop

What we removed

Early versions routed commands through a ROS bridge over SSH. Once every skill ran on the workstation and spoke DDS directly, the bridge did nothing but add a hop and a failure mode. It was removed. If you are reading older notes in the repository history that mention rosbridge, they describe a version that no longer exists.
