Robotics research · Quadruped autonomy

A robot that takes orders in plain language.

A Unitree Go2 quadruped, a Telegram chat, and a language model that is allowed to do exactly one thing: pick a skill and run it. We are studying whether that restriction has to be built into the system, or whether asking politely is enough.

The question

Do rules in a prompt actually constrain a model?

Every agent framework tells the model what it may not do. We wanted to know whether that instruction holds when the model has a shell. So we built the same robot twice: once where the restriction is written in the prompt, and once where the tools simply are not there.

Approach 1 — architectural

The tools are removed

The agent runs under a restricted tool profile. Raw shell and file editing are denied at the framework level, leaving one dispatch tool that can call a validated skill and nothing else. The rule cannot be argued with, because there is no tool to argue with.

  • run_skill
  • exec
  • write
  • edit
  • apply_patch
Approach 2 — prompt only

The tools are there, and we ask nicely

The agent keeps full shell access and is told in its system prompt to use the skill library, one skill per turn. This is how most agent deployments actually work. The question is what happens when the shortest path to the goal runs straight through the rule.

  • run_skill
  • exec
  • write
  • edit
  • apply_patch

What is running

The stack

Nothing here is simulated. A lab workstation talks to the robot over a wired DDS link and to the operator over Telegram. The language model never touches a motor — it selects a Python skill, and the skill talks to the robot.

  • Robot — Unitree Go2, high-level sport controller over DDS
  • Workstation — Dell Precision 3660, Ubuntu 20.04, RTX 4090
  • Agent framework — OpenClaw, gateway with tool-profile gating
  • Model — Claude Sonnet via the Anthropic API
  • Interface — Telegram bot, text in and text out
  • Perception — YOLOv8-nano, single-frame detection at 640 px

Honest accounting

Known limitations

  • Locomotion is dead-reckoned. Distance is estimated from velocity and duration, so error accumulates and there is no map.
  • There is no obstacle avoidance. The robot will walk into things.
  • Detection runs on a single frame at a single moment. A person who moves between the turn and the capture is missed.
  • A failed skill has no recovery path. The model is told it failed and decides what to do next with no fallback behaviour.
  • Changing a skill mid-session leaves the model replaying stale commands. A fresh session is required after any edit.
