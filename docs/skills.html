Skill library

Every skill follows the same contract.

A skill is a folder with a description the model reads and a script the machine runs. The description is the interface. The script is the implementation. Neither knows about the other's internals.

The contract

Anatomy of a skill

Each skill lives in its own directory in the agent workspace. The gateway reads SKILL.md at startup and puts it in front of the model, the model never sees the Python. Everything the model needs in order to choose correctly has to be in that Markdown file, and everything it must not get wrong has to be in the script.

Every skill ends by printing one line beginning with RESULT, followed by space-separated key=value pairs. That line is the only thing the model reads back. Free-form prose output invites the model to interpret, a fixed schema does not.

Worked example

walk, in full

- direction: forward | turn_left | turn_right

# Two things this script exists to get right:
#  1. Move() must be resent at ~10 Hz for the full duration.
#     A single call stops after about one second.

Design rule

Complexity belongs in the skill, not the runner

There is a constant temptation to make the dispatch tool smarter — let it accept a small script, a sequence, a conditional. Every one of those additions reopens the hole that Approach 1 exists to close. If the runner can execute arbitrary logic, the tool profile is decorative. So the runner stays minimal: it takes a skill name and parameters, validates them, runs one script, returns one line. Anything that needs to be cleverer than that becomes a new skill, reviewed and tested like any other.
